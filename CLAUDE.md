# Dory — project context for people and AI agents

Read this first, then `README.md` (product, architecture, how to use it with Google Meet).

## What this is

Dory is an AI coworker for teams on Discord (also Slack, LINE, Telegram and WhatsApp) with a web command
center. Two packages: `src/meeting_scribe/` (the FastAPI web service: the public site, `/start`, `/center`,
`/hub`, `/pm` and the Meeting Scribe recorder) and `src/dory/` (the bot and everything it does).

The Meeting Scribe recorder (`/recorder`): a host opens it next to a Google Meet, clicks Record and shares the Meet tab with
"Share tab audio". The browser mixes tab audio + mic and uploads ~45 s audio segments.
The server transcribes each segment in Thai with speaker labels (Gemini on Vertex AI), and on
Stop an ADK multi-agent summarizer produces decisions, action items and speaker names, saves
them to Firestore and posts a Discord embed with the transcript attached.

- Code, comments, docs and UI are **English**. Meeting audio, transcripts and summaries are **Thai**.
- Repo: https://github.com/TheFrontier-AI/dory-personal-assistant

## Pipeline in one line

Browser chunk → `POST /api/meetings/{id}/chunks` → ffmpeg → 16 kHz FLAC → Cloud Storage →
Gemini (`gemini-3.5-flash`, transcribe + diarize) → Firestore. On Stop: `/finish` → Pub/Sub →
`/pubsub/finalize` (OIDC-verified) → ADK `[decisions ‖ action items ‖ speaker names]` on
`gemini-3.5-flash` → synthesizer on `gemini-3.1-pro-preview` → Firestore → Discord webhook.

## Dory (`src/dory/`) — second package

Discord bot "ดอรี่" (display name Dory), **multi-tenant**: tenant key = Discord guild id; any server adds it via the public invite and gets an isolated ledger and settings with no setup. Receipt photos to an expense ledger, Thai executive Q&A. Env vars are all
`DORY_*` (see `.env.example`). `DORY_STORE=sqlite` (default) or `firestore`. Deployment is prepared but **not run**: `Dockerfile.dory`, `cloudbuild.dory.yaml`, `scripts/deploy_dory.sh`
(dry-run by default, `--apply` to execute; README "Deploying Dory"). Never use `--apply` without human approval. The system's base language is **English** (`i18n.DEFAULT_LANGUAGE`; an unchosen server runs in English, never follow-the-words). Language is set at TWO levels only (2026-10-18): the **company language** for the whole server (`/company-language`, typed `use English everywhere`, hub, `language_ask.py` select menu on join; `default_language` + `language_chosen` in the guild doc) and each person's **personal language** (`/language`, typed `talk to me in Thai`, stored in the profile). There is no per-channel language any more (`channel_languages` is ignored). Every typed command has Thai and English forms; Dory always *understands* Thai and English, the settings decide what she *says*. See Languages below. All fixed user-facing strings live in `src/dory/i18n.py` (`t(key, lang, **fmt)`; Thai text is the original wording, add both languages for every new string); LLM prompts take a `language` argument.

### Deploying the monitor (Dory workflow monitor)

- **The change-outbox re-key is NOT behind a flag.** Until `scripts/dory_outbox_migrate.py --apply` runs, the
  changes recorded before it (guild 0) are missing from the `/center` change list, are not resent, alerted or
  pruned, and a typed or reaction ack on an old notice misses (button clicks and `ack(org_id=...)` still work
  through the legacy fallback in `ChangeOutbox._update`). Run the migration as a dry run first
  (`uv run python scripts/dory_outbox_migrate.py`, counts only), then `--apply` with human approval as soon as
  every process (web, bot, platform bridge) runs the new code; re-run it once the old revisions are gone (old
  code may still record under guild 0). Re-runs are safe.
- Enable the two flags together: `MONITOR_ENABLED` (web service) and `DORY_MONITOR_ENABLED` (bot worker pool
  and platform bridges). Web only: no heartbeat is written, so every org with a Discord workspace shows Dory

- Not gated by the flags either: the bot deletes finished web -> Discord action records 30 days after they were
  queued (`actions.KEEP_DAYS`, hourly per server), starting on its first tick after the deploy (approved in

### Languages (Dory)

**Company language + personal language** (`audience.py`, 2026-10-17/18). The server's chosen language is THE language of everything Dory says, types and produces; a person may add a personal language (profile) and an executive can force "company language only" (guild `language_mode`, or per meeting by the chair). Per message the languages are: company first, then the personal language of each person involved (recipient, and the giver when a line goes back to them) when it differs, at most three; the model is told to reply in the company language and, with 2+ languages, to repeat in the next one (`second_language_rule`); a second-language block is labelled `*(Thai translation)*` and captions use `↳ (Thai translation) …` so a reader who does not know the script sees it is a translation. Nothing is decided from the language somebody wrote or spoke or from the Discord locale (an unchosen server runs in English); listening never changes. Voice: the spoken hint (`qa.spoken_hint`) follows the company language (a Thai hint used to pull answers into Thai) and a translate-if-wrong-script safety net guards both voice paths. Use `AudienceMixin.langs_for` / `_deliver_langs` and `audience.tt` / `render`, never `profile.language` or `channel_languages` directly.

Two tiers. **Primary** `th`, `en`: every string hand-written in `i18n.CATALOG`. **Second tier** `zh hi ms id vi ko ja`:
fixed strings come from generated `src/dory/locales/<lang>.json`; the model is told `Reply ONLY in <language>` at the
top of the persona (`i18n.reply_language_line`, `qa.persona`) and otherwise gets the English prompt blocks. Code that
branches on the language must use `base_lang(lang)` / `lang == "th"` (never `lang == "en"`, which would send `ja` to Thai)
and `lang_name(lang)` for prompts that name the language. Thai particles only apply to `th`. Voice: `speech._LANG_CODES`
(+ `_VOICE_FALLBACK`: ms -> id-ID, no ms-MY Chirp 3 HD voices), `live_voice.build_instruction_en(reply_lang=)`. Documents:
`pdf_report.find_fonts(lang=)` / `script_fonts` (Noto CJK faces extracted from the .ttc into the user cache, Devanagari),
`font_note` when the fonts are missing (labels fall back to English), `cards.card_fonts(lang)`, `deck.DECK_FONTS`. The hub UI
stays Thai/English but its language selects list all ten. Adding a catalog key: add th + en, then re-run the translate script.

### Memory retention and data stores (Dory)

- What the staff tell Dory is the **company's asset**: team memory is kept **forever by default** (guild
  `memory_retention_days` = 0, `guild_settings.effective_retention_days` maps it to a 10-year window for
  readers, imports and purges; the hub offers "Keep forever (company asset)" first). A positive value is
  an explicit company choice to purge older memory. Nothing is deleted when a company stops using the
  service except by that company's own request.
- The Discord bot, the web center (`/center`, `/pm`, web chat) and the platform bridges MUST point at the
  SAME store (`DORY_STORE` + `DORY_DB_PATH` locally, Firestore in production): a second process with
  its own `data/ledger.db` sees an empty company. A person is one identity across them: the org member's
  `email` (web, Google sign-in) must carry their `discord_user_id` (member link), otherwise "my tasks" on
  the web is empty while Discord knows them.

### One brain, every platform (rule for new features)

Dory also runs on Slack, LINE, Telegram and WhatsApp (`src/dory/platforms/`, `python -m dory.platforms`,
setup in `docs/platforms/`). Every new feature must be reachable from all of them, written once. Design and
build order: `docs/superpowers/specs/2026-10-18-dory-workspace-parity-design.md`. In short:

- Feature logic lives in a module that does **not import `discord`** (ids, text, a `Workspace`).
- People, rooms, posts, DMs, files, buttons and schedules go through the `Workspace` interface, never
  `discord.*` / `slack_sdk` / a platform API inside a tool or feature module. Until `Workspace` lands, keep new
  Discord glue in a thin `*_bot.py` mixin and the logic in the pure module, so moving it is mechanical.
- A capability a platform lacks is declared (`supports(...)` False) and the tool is left out; never fake it.
- Memory scope stays fail-closed: unknown room audience = that room's own memory only.
- Meetings: Dory's own store + reminders everywhere; Google Calendar (per-user Google OAuth) is the calendar.
- Platform tenant ids use the one workspace id scheme (`orgs.workspace_memory_id` / `namespaced_id`).
- The org is the centre: a person is one `orgs.Member` with verified platform identities; cross-platform answers
  only in a 1:1 with a verified member, rooms with an unknown audience use their own memory only.
- Google Calendar / Meet need a separate per-member Calendar consent (Google login alone gives no Calendar access).

## Credentials and safety rules

- `.env` holds `DISCORD_WEBHOOK_URL`, a GitHub token (`GH_TOKEN`) and GCP settings. **Never** print,
  log, echo, paste into chat, commit, or put any of these values on a command line. Refer to them by
  key name only.
- Before any commit: `git status` and `git diff --cached`. `.env`, `samples/` and `*.json` key files
  must never be staged.
- Do not create service-account key files. Use `gcloud auth login` + `gcloud auth application-default login`.
- `gcloud run deploy --source .` uploads the directory; `.gcloudignore` includes `.gitignore` (so `.env`
  is excluded) and drops `.claude/`. Confirm before deploying. Plain `gcloud run deploy meeting-scribe
  --source . --region asia-southeast1` keeps the existing env vars and secrets (no new secret version).
- `scripts/deploy.sh` and `scripts/deploy_dory.sh` add a Secret Manager version only when a secret
  has none (`--rotate-token` for the Discord token); values come from the environment or `.env`
  via stdin and are never echoed. Run them only intentionally.
- **Never set `USE_PUBSUB=true` locally**: it routes finalize to the production push endpoint.
  Local runs use `STORE=memory` and the default `USE_PUBSUB=false`.
- Re-transcribing chunks costs Vertex quota. 3–4 chunks is fine; ask before a whole meeting.
- Ask a human before anything destructive, costly or production-affecting: deploys, new secret
  versions, deleting data, posting to Discord, changing Firestore records.

## Known limitations — do not "fix" without asking

- No auth on the web app or API; keep the URL private.
- About 0.1 s of audio is lost at each 45 s segment boundary.
- No retention policy on audio or Firestore (deleting data needs approval).
- Desktop Chrome/Edge only (tab-audio capture).
- **Limits and locks are in the shared store** (issues #19, #20; they survive restarts and hold
  across instances): 5 organizations per person; sign-up `POST /orgs` = ONE `DocStore.transact`
  (claim record `dory_org_signups` (sha256 of email + name) -> the org, same name within
  `ORG_REPEAT_WINDOW` of its `created_at` = that org, then the cap, then `ORG_LIMITER`, then
  `OrgStore._tx_create`); every rate limit is a `meeting_scribe.limits.TokenBucket` (DocStore
  `dory_rate_limits`, sha256 keys, wall clock): `ORG_LIMITER` (burst 3, then 1 per 10 s),
  `CHAT_LIMITER` (web chat and voice transcription: burst `CHAT_PER_HOUR` 30, then 1 per 2 min),
  the monitor's `LIMITER` (burst 3, 1 per 2 s); the recorder's finalize = a lease on the meeting
  (`finalize_lease`, `FINALIZE_LEASE_S` 900, `claim_finalize` / `release_finalize`; a second
  finalizer gets `FinalizeBusy`, Pub/Sub a 409 and redelivery); the link-code guessing limit
  (`IdentityLinks.take_try`). **Still per process, so `max-instances=1` stays until reviewed:**
  `OrgStore.save` and member edits (process lock, last writer wins), `center`'s in-process
  `lru_cache` collaborators, the platform bridge's message dedupe and
  reply windows, the bot's `memory_index` / `recent` (one bot process).
